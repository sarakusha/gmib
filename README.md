# О программе

Название GMIB происходит от начальных букв Graphical User Interface of
[Management Information Base](https://ru.wikipedia.org/wiki/Management_Information_Base)
(графический интерфейс для базы управляющей информации). Изначально данное ПО разрабатывалось для
управления периферийным оборудованием производства компании Ната-Инфо, а именно для опроса состояния
оборудования (хранящегося в различных переменных), изменения его параметров, выполнения встроенных
подпрограмм на оборудовании, обновления и записи аппаратного ПО. В качестве сети связи
использовалась промышленная сеть на собственном проприетарном протоколе NIBUS работающем по
стандарту физического уровня для асинхронных интерфейсов RS-485. Вот цитата из описания протокола
NIBUS:

> Протокол NiBUS обеспечивает набор коммуникационных сервисов, которые позволяют пользовательскому
> приложению в устройстве посылать и получать сообщения от других устройств в сети без необходимости
> знать топологию сети или имена, адреса или функции других устройств. При этом опционально может
> обеспечиваться сквозное подтверждение приема сообщений. Поддержка сетевых управляющих сервисов
> позволяет средствам сетевого управления взаимодействовать с устройствами по сети, включая
> реконфигурацию сетевых параметров, загрузки пользовательских приложений, и старта/стопа/рестарта
> пользовательских приложений устройств. Протокол NiBUS является многоуровневым, пакетно
> ориентированным, одноранговым коммуникационным протоколом. Подобно общепринятым протоколам
> Ethernet и Internet он придерживается рекомендаций многоуровневой архитектуры эталонной модели ISO
> OSI. Однако протокол NiBUS спроектирован для специфичных требований систем управления, а не систем
> обработки данных. Адаптируя протокол для целей управления на каждом OSI уровне, протокол NiBUS
> обеспечивает решение, обеспечивающее надежность, производительность и устойчивость, требуемые
> управляющими приложениями.

Каждый тип оборудования, поддерживающий управление с помощью протокола NIBUS, хранил описание своей
управляющей информации в специальных MIB-файлах с описанием схемы в формате XSD. Для опроса и
управления оборудованием можно было воспользоваться инструментом для командной строки Windows,
указав нужный MIB-файл и требуемую команду, что было несколько неудобно и сложно, особенно для
неподготовленных пользователей. Данная программа позволяла автоматически обнаруживать и
идентифицировать подключенные периферийные устройства, предоставляла удобный интерфейс для
управления ими, была мультиплатформенной и поддерживала основные ОС: Windows, Linux, macOS. В
дальнейшем функционал программы постоянно расширялся и стал поддерживать в том числе и такие функции
как:

- подключение устройств по USB и Ethernet;
- задание параметров (размер, расположение, яркость, адреса устройств) для управления подключенными
  видеоэкранами;
- автоматическое управление яркостью видеоэкранов по показаниям датчиков освещенности или положению
  солнца, с указанием географических координат установленного оборудования;
- периодическое получение и сохранение телеметрии, снижение яркости видеоэкранов при превышении
  критической температуры оборудования;
- автоматический запуск, автообновление, авторизация и аутентификация, удаленное подключение и
  управление;
- поддержка популярных устройств и видеоэкранов сторонних производителей; показ графической
  информации на видеоэкранах, вывод HTML-страниц;
- создание плейлистов с видеоконтентом и воспроизведение видео на экранах;
- планировщик заданий;

Основной режим работы программы — автономный, «настроил и забыл». Оператор подключает оборудование,
задает настройки, включает автозапуск. Далее программа самостоятельно отслеживает текущий статус
оборудования, изменяет параметры согласно заданному плану или в случае нештатных ситуаций.

# Установка и удаление программы

## На Windows

Для установки программы на Windows необходимо запустить установщик
[`gmib-setup-<версия>.exe`](https://github.com/sarakusha/gmib/releases), где версия это три группы
номеров версии (например 4.2.0). Программа автоматически установится в папку по пути
`%LocalAppData%\Programs\gmib`. Данные и настройки программы хранятся в папке `%APPDATA%\gmib`.
Удаление программы осуществляется стандартными средствами Windows через _Установка и удаление
программ_ в _Параметрах системы_.

> Актуальные релизные сборки Windows рассчитаны на 64-разрядные версии ОС.

## На ОС семейства Linux

Для установки и запуска ПО на Linux используется переносимый формат
[AppImage](https://ru.wikipedia.org/wiki/AppImage), когда вся программа хранится в одном сжатом
файле. Вам нужно скопировать файл
[`gmib-x64.AppImage` или `gmib-arm64.AppImage`](https://github.com/sarakusha/gmib/releases) в
домашнюю папку пользователя (или любое другое место на диске), сделать файл исполняемым
(`chmod +x gmib-*.AppImage`) и запустить. При первом запуске программа сама создаст нужные ярлыки в
меню приложений системы. Данные и настройки программы хранятся в папке `$XDG_CONFIG_HOME/gmib` или
`~/.config/gmib`. Также, если Вы будете использовать функции плеера, необходимо установить `ffmpeg`
включая `ffprobe`. Например в Ubuntu это можно сделать командой `sudo apt install ffmpeg`. Он
используется для конвертации медиа-файлов. Для удаления программы просто удалите файл AppImage,
также можете удалить папку с данными.
Также может понадобиться добавление текущего пользователя в группу dialout:

```bash
> sudo usermod -a -G dialout $USER
```

### Экспериментальный kiosk-режим Linux

На Linux GMIB можно запустить с параметром `--kiosk-mode` или переменной окружения
`GMIB_KIOSK_MODE=1`. При действующей лицензии локальное окно управления и системный трей скрыты, а
управление выполняется с другого GMIB через удаленное подключение. Если лицензия отсутствует или
требует восстановления, локально открывается диалог активации; им можно управлять клавишами
`Tab`, `Enter` и `Space`, даже когда аппаратный курсор скрыт. Существующие окна HTML-вывода продолжают
создаваться из сохраненной конфигурации экранов; для Cage/Wayland следует использовать один дисплей
и одно активное полноэкранное окно вывода.

Пример ручного запуска внутри Cage:

```bash
cage -- gmib-x86_64.AppImage --no-sandbox --kiosk-mode --ozone-platform=wayland
```

Kiosk-режим не предназначен для конфигураций с несколькими произвольно расположенными окнами. Для
таких конфигураций на Linux используйте обычный запуск GMIB и точное позиционирование через X11.
Устройства NovaStar на RNDIS или IPv4 link-local (`169.254.0.0/16`) обслуживаются локальным
экземпляром GMIB и не перенаправляются на выбранный в общей сети master. Это правило действует и в
обычном режиме GMIB, поскольку такой интерфейс недоступен с другого компьютера.

Для тестового компьютера на базе Ubuntu Server подготовьте исполняемый AppImage в
`/opt/gmib/gmib.AppImage`, затем установите Cage-сеанс:

```bash
sudo scripts/setup-linux-kiosk.sh --user "$USER"
systemctl status gmib-cage@tty1.service
```

Скрипт устанавливает минимальный Wayland/Mesa runtime, выдаёт пользователю доступ к DRM, serial и
поддерживаемым FTDI USB-устройствам (`0403:6001` и `0403:6015`), скрывает аппаратный курсор Cage и
создаёт перезапускаемый systemd-сервис на `tty1`.
Для проверки без немедленного запуска используйте `--no-start`. Другой AppImage или распакованный
бинарный файл можно указать через `--executable /absolute/path`.

Для серийной установки Ubuntu Server, GMIB, Cage и Pritunl Client используйте сборщик образа и
безопасную первичную регистрацию из [`deploy/kiosk`](deploy/kiosk/README.ru.md) (также доступна
[английская инструкция](deploy/kiosk/README.md)). Образ не содержит постоянного API-ключа: при первом
запуске оператор вводит короткий одноразовый код, после чего сервер привязывает его к устройству,
персональный VPN-профиль импортируется, а временный архив удаляется.
Установщик также ставит штатный Ubuntu-пакет `ffmpeg`: GMIB использует системные
`/usr/bin/ffmpeg` и `/usr/bin/ffprobe` для конвертации и анализа медиафайлов.
Новый kiosk-образ настраивает `ru_RU.UTF-8` и консольный кириллический шрифт, а также устанавливает
Zabbix Agent 2 7.4 выключенным. После успешного подключения VPN enrollment-сервер может включить
агент только для исходящих active checks; входящий порт 10050 не открывается.
Для подключения клиент должен предоставить адрес сервера/proxy Zabbix (не URL веб-интерфейса),
порт active checks (обычно 10051), PSK identity и hex-ключ из настроек авторегистрации,
а также согласовать metadata, группы и активный Linux-шаблон. Его администратор настраивает
действие авторегистрации по `product=gmib;role=kiosk` и разрешает доступ из сети/VPN киоска.
Параметры задаются на app-server через `npm run enrollment:zabbix -- set <ORG_ID> …`,
а коды создаются с `npm run enrollment:create -- gmib 10 60 --organization <ORG_ID>`.
Подробный checklist и примеры CLI находятся в README app-server; оператор киоска вводит только код.
Организация без настроек не включает мониторинг. Уже развёрнутые устройства автоматически
не перенастраиваются; локальные команды описаны в [инструкции kiosk](deploy/kiosk/README.ru.md).

Если при подключении устройства оно не распознается и в журнале программы выдается ошибка `LIBUSB_ERROR_ACCESS`,
нужно создать файл `/etc/udev/rules.d/100-gmib.rules` и добавить в него по строке для каждого вида устройств.
Узнайте `VID` и `PID` устройства командой:

```bash
> lsusb

[Вывод команды]
Bus 007 Device 003: ID 10c4:ea60 Silicon Labs CP210x UART Bridge
Bus 007 Device 002: ID 05e3:0608 Genesys Logic, Inc. Hub
Bus 007 Device 001: ID 1d6b:0002 Linux Foundation 2.0 root hub
Bus 004 Device 001: ID 1d6b:0001 Linux Foundation 1.1 root hub
Bus 002 Device 001: ID 1d6b:0002 Linux Foundation 2.0 root hub
Bus 003 Device 001: ID 1d6b:0001 Linux Foundation 1.1 root hub
Bus 001 Device 001: ID 1d6b:0002 Linux Foundation 2.0 root hub
```

Наше устройство здесь `Silicon Labs CP210x UART Bridge` и его `VID=10c4`, а `PID=ea60`.
Тогда строчка будет выглядеть так:

```
SUBSYSTEM=="usb", ATTRS{idVendor}=="10c4",   ATTRS{idProduct}=="ea60", OWNER="user",   GROUP="plugdev", TAG+="uaccess"
```

Значение OWNER должно содержать имя текущего пользователя.

## На macOS

На macOS вам нужно открыть файл
[`gmib-[версия].dmg` или `gmib-[версия]-arm64.dmg`](https://github.com/sarakusha/gmib/releases) и
переместить приложение в папку `Applications`. Данные и настройки программы хранятся в папке
`~/Library/Application Support/gmib`. Чтобы удалить программу просто удалите её из папки
`Applications`. Не забудьте удалить папку с данными, если больше не будете пользоваться программой.

macOS помечает файлы из интернета (особенно неподписанные приложения с GitHub) как потенциально
опасные с помощью атрибута карантина `com.apple.quarantine`. Это приводит к блокировке, даже если
файл цел и не повреждён. Чтобы снять эту блокировку, нужно удалить атрибут карантина с помощью
команды в терминале:

`sudo xattr -r -d com.apple.quarantine /Applications/gmib.app`

Инструкция по подписи macOS-релизов для автообновления: [docs/macos-code-signing.md](docs/macos-code-signing.md).

## Активация лицензии

Чтобы получить доступ к расширенным возможностям необходимо активировать лицензию на устройстве.
Ключ активации представляет собой строку из цифр и латинских букв длиной 12 символов и разделителей.
Чтобы активировать или проверить активацию, выберите в меню _Помощь_ пункт _Лицензия_. Если
активация уже выполнена, будут видны тип лицензии и частично ключ активации.

Для активации выберите пункт _Активировать лицензию_ и введите ключ в открывшемся диалоге. Перед
активацией убедитесь, что есть соединение с Интернетом. После успешной активации программа
автоматически перезапустится. Если сервер уже подтвердил лицензию, кратковременная ошибка при
завершении обмена не требует повторного ввода ключа.

После активации gmib периодически подтверждает регистрацию на сервере лицензирования. Если для
устройства на сервере включен флаг автообновления, gmib сохраняет этот флаг локально, проверяет
доступность новой версии и при наличии обновления скачивает его с последующим перезапуском.

При первом запуске новой версии существующая активация обновляется автоматически; для этого требуется
соединение с Интернетом. После успешного обновления действующая лицензия допускает запуск без сети.
Если сервер временно недоступен, в диалоге активации можно повторить проверку сохранённой лицензии без
повторного ввода ключа. После окончания срока приложение предложит продлить или повторно активировать
лицензию. Если условия лицензии изменились во время работы, gmib сообщит, что их нужно применить
перезапуском. Управление NovaStar Taurus и плагины доступны с лицензией Plus или выше.

> Если активировать несколько устройств одним ключом, только последнее устройство будет активировано.
> При клонировании устройств активный статус также сохранится только у одного экземпляра.

## Обновление ПО

Убедитесь что у вас есть соединение с Интернетом, откройте программу и выберите в меню _Помощь_
пункт _Проверить обновления_. Если доступна более новая версия программы, вам будет предложено
загрузить обновление. После загрузки обновления программа автоматически перезапустится. Обновление
также можно запустить на удаленном устройстве, если оно доступно через удаленное управление.
При включенном на сервере лицензирования автообновлении ручная проверка не требуется.

На Linux для обновления AppImage пользователь, запускающий gmib, должен иметь права записи в файл
AppImage и его каталог. Установщик gmib-kiosk назначает владельцем `/opt/gmib` пользователя kiosk.
Окно ошибки обновления не блокирует API и удалённое управление.

# Использование программы

## <a name="gui">Интерфейс</a>

Интерфейс программы выглядит практически одинаково на всех платформах. Если на какой-то платформе
наблюдается отличие, об этом будет упомянуто дополнительно. Видеоплеер открывается в собственном
окне и будет описан отдельно.

> Некоторые элементы интерфейса доступны только для лицензий с определенными планами.

Интерфейс приложения включает в себя _Меню_, _Навигационную панель_ (**<abbr>НП</abbr>**) в левой
части окна и _Рабочее пространство_ (**<abbr>РП</abbr>**) с названием приложения и текущей версией.
РП может содержать _Панель инструментов_ (**<abbr>ПИ</abbr>**) и _Вкладки_, а содержание зависит от
выбранного пункта в НП. Чтобы понять, за что отвечает та или иная кнопка в ПИ достаточно подвести
курсор к выбранной кнопке и прочитать "всплывающую" подсказку.

> Некоторые пункты НП или группы свойств могут содержать вложенные списки. Тогда рядом с названием
> пункта или группы отображается символы <span class="material-symbols-outlined">expand_more</span>
> или <span class="material-symbols-outlined">expand_less</span> кликнув по которым можно
> свернуть/развернуть вложенный список. Саму НП также можно скрыть/отобразить кликнув по символу
> <span class="material-symbols-outlined">chevron_left</span> или
> <span class="material-symbols-outlined">menu</span>.

## <a name="devices-anchor">Устройства</a>

При запуске и в процессе работы приложение будет подключать доступные устройства и устройства
перечисленные в конфигурации экранов и добавлять их в список Устройства в НП. При выборе устройства
в РП могут быть доступны следующие вкладки:

Кнопка _Повторить поиск_ в заголовке списка немедленно повторяет поиск устройств NIBUS, NovaStar и
Taurus. Пока сетевой поиск NovaStar/Taurus выполняется, вместо значка обновления показывается
индикатор.

### <a name="props-anchor">Вкладка _Свойства_</a>

Каждое такое устройство из списка можно выбрать кликнув по нему мышью и в области РП будут
отображаться свойства выбранного устройства, часть из которых можно изменять пользователю.

> Изменение свойств устройства относится к "тонкой" настройке, и должно выполняться
> квалифицированным специалистом. Рядовым пользователям при повседневной эксплуатации обычно не
> требуется изменять эти свойства. Также некоторые свойства, такие как яркость управляются
> централизованно и не должны изменяться для индивидуальных устройств.

Если свойств достаточно много, то они могут быть сгруппированы по группам.

На панели инструментов вкладки Свойства могут быть доступны следующие действия:

- &nbsp;<span class="material-symbols-outlined">system_update_alt</span> Загрузить свойства из
  файла. <br/> Загружает сохраненные ранее свойства из указанного файла.
- &nbsp;<span class="material-symbols-outlined">save</span>Сохранить выбранные свойства в файл.
  <br/> Позволяет сохранить все или указанные значения изменяемых свойств в указанный файл.
- &nbsp;<span class="material-symbols-outlined">refresh</span>Обновить свойства. <br/> Повторно
  перечитать все свойства с устройства.
- &nbsp;<span class="material-symbols-outlined">search</span>Поиск новых устройств. <br/> Открывает
  диалог поиска устройств в сети NIBUS по типу или адресу (см. ниже)

### Диалог _Поиск новых устройств_

Диалог _Поиск устройств_ можно вызвать кликнув по символу
<span class="material-symbols-outlined">search</span> на панели инструментов. С его помощью можно
найти устройства, подключенные к сети NIBUS по RS-485 интерфейсу. Обычно Ваш компьютер должен быть
подключен к общей сети посредством устройства Siolynx.

Поиск устройств можно осуществить по его _типу_ или по _адресу_. Если вы подключены к нескольким
сетям, можно выбрать активное _соединение_, либо искать во всех сетях. Если используется поиск по
типу устройства, нужно выбрать искомый тип из выпадающего списка. Если поиск по адресу, то укажите
искомый адрес. Если все задано, можно начать поиск кликнув кнопку с надписью _Начать_. Если поиск
затянулся, его можно остановить кликнув на _Остановить_. Процесс поиска сопровождается движением
полоски индикатора выполнения. Также в окне будут появляться обнаруженные устройства. Их можно
добавить в общий список устройств кликнув по символу плюс рядом с устройством.

> Если адрес устройства перечислен в свойствах экрана, его поиск будет осуществляться автоматически.

### Вкладка _Телеметрия_

Для некоторых устройств/видеоэкранов доступно получение телеметрии от каждого модуля, которая может
содержать такие параметры как:

- напряжение
- температура
- версия прошивки
- цветовые координаты и т.д.

Для плееров NovaStar Taurus опрос выполняется через штатное авторизованное Taurus-подключение, без
порта 5200 и ADB. Принимающие карты располагаются в сетке согласно физической топологии экрана; для
каждой карты отображаются номер Ethernet-порта и номер в цепочке, состояние, температура, напряжение
и доступные версии FPGA/MCU. Порты и карты нумеруются с 1, как в списке применения NCP. Значение
`-255`, возвращаемое Taurus для недоступного датчика, выводится как отсутствие данных.

На панели инструментов вкладки _Телеметрия_ доступны следующие действия:

- &nbsp;<span class="material-symbols-outlined"> filter_4 </span> Выбрать запрашиваемые
  переменные.<br/> Вызывает диалог выбора интересующих параметров (отображает количество выбранных
  параметров)
- &nbsp;<span class="material-symbols-outlined">refresh</span> Запустить опрос модулей. <br/>
  Запускается запрос данных телеметрии указанного диапазона экрана.

Также используя слайдеры можно задать диапазон опрашиваемых модулей по рядам и строкам (на некоторых
устройствах может быть недоступно).

В процессе опроса данные телеметрии будут выдаваться в табличном виде.

> Чем больше запрашиваемых параметров тем дольше производится опрос. Указывайте только интересующие
> вас параметры.

## Вывод

Если выбрать данный пункт в НП, то слева можно увидеть список переключателей тестовых
режимов/виджетов, а справа - вкладки с параметрами доступных экранов и окном просмотра.
Включение/выключение переключателя отображает/скрывает динамический тест или виджет на выбранном
экране и отображает состояние вывода в окне просмотра.

> Качество картинки в окне просмотра может зависеть от качества канала до удаленного устройства.
> Если соединение не удалось и картинка не отображается, попробуйте перегрузить окно комбинацией
> клавиш `Ctrl` + `R`.

Если выбранный дисплей временно отключен, тестовое окно и область вывода плеера не переносятся на
другой монитор. После повторного подключения дисплея GMIB автоматически восстанавливает на нем
вывод и заново подключает локальный и удаленный WebRTC-предпросмотр; переключать вывод вручную не
требуется.

Предпросмотр экрана захватывает окно вывода целиком, сохраняя его пропорции, и показывает весь
кадр без обрезки, в том числе для узких LED-экранов. Если пропорции окна и области предпросмотра
различаются, вокруг изображения остаются поля. Предпросмотр плеера передаёт исходный видеопоток;
его отображение учитывает выбранный режим масштабирования вывода.
При удалённом подключении предпросмотр экрана и плеера адаптируется к доступной скорости канала,
балансируя разрешение и частоту кадров. Это не влияет на локальный вывод устройства.
Краткий обрыв WebRTC-предпросмотра окна вывода не перезапускает захват сразу: GMIB ждёт
восстановления связи до 10 секунд. Если связь не восстановилась, предпросмотр подключается
заново автоматически. Медленное подключение не сбрасывается повторными запросами захвата.
Для ожидания на обеих сторонах требуется обновить также удалённый GMIB; обмен сообщениями
предпросмотра остаётся совместимым с предыдущими версиями.

На панели инструментов расположены следующие элементы:

- &nbsp;<span class="material-symbols-outlined"> refresh </span> Обновить текущий вывод.<br/>
  Обновляет текущее окно вывода, если оно есть.
- &nbsp;<span class="material-symbols-outlined"> brightness_auto </span> Автояркость.<br/>
  Включает/выключает режим автояркости для выбранного экрана. Если экран в режиме автояркости, то вы
  не можете указать индивидуальную яркость, она задается централизованно.
- **75%** Текущая яркость.<br/> Отображает текущую яркость в процентах
- &nbsp;<span class="material-symbols-outlined"> brightness_4 </span> Уменьшить на единицу.<br/>
  Уменьшает яркость на один процентный пункт. Не активен в режиме автояркость.
- **Слайдер/ползунок**.<br/> Задать яркость. Не активен в режиме автояркость.
- &nbsp;<span class="material-symbols-outlined"> brightness_high </span> Увеличить на единицу.<br/>
  Увеличивает яркость на один процентный пункт. Не активен в режиме автояркость.

Создать новый экран можно кликнув на вкладке по символу <span class="material-symbols-outlined">
add_to_queue </span>, удалить - по <span class="material-symbols-outlined"> close </span>.

Для просмотра или редактирования параметров экрана раскройте форму кликнув по иконке
<span class="material-symbols-outlined"> expand_more </span> справа от надписи _Свойства_.
Параметры позволяют задать размеры экрана в пикселях, размеры модуля/платы, отступ верхнего левого
угла экрана и дисплей, на который выводить изображение. Дисплей можно указать как _основной_ или
_второстепенный_, либо по его идентификатору. Чтобы узнать идентификатор дисплея, его необходимо
подключить, тогда его номер отобразится в списке доступных.

Также важно задать логические или сетевые адреса минихостов, если вы хотите централизованно
управлять их яркостью и другими параметрами. Каждый экран должен содержать непересекающийся список
адресов. Устройства с указанными адресами будут автоматически обнаружены и включены в список
устройств.

Плееры NovaStar Taurus (в том числе TB60) обнаруживаются по Taurus API. Если тот же плеер также
отвечает на устаревшем порту 5200, gmib скрывает этот дубликат и использует Taurus-подключение.
Отключенный Taurus удаляется из списка после ближайшего успешного цикла поиска; кнопка _Повторить
поиск_ запускает такой цикл немедленно.
Откройте найденный плеер в списке устройств и один раз введите его пароль: он сохраняется только в
локальных настройках GMIB. После входа GMIB читает яркость и встроенный датчик освещённости через
Taurus API. Яркость, заданная вручную в свойствах Taurus, сохраняется в аппаратной памяти плеера и
восстанавливается после перезапуска. Общая и автоматическая яркость применяется без постоянной
записи во flash-память. GMIB читает текущий режим показа, но не переключает источник при подключении.
На странице свойств можно явно выбрать встроенный плеер, HDMI, HDMI с автоматическим возвратом на
встроенный плеер или расписание Taurus; там же показывается фактически активный источник.

На вкладке _Конфигурация_ можно прочитать физическую топологию LED-экрана и применить файл NovaLCT
`*.scr`. Перед записью GMIB показывает текущие и новые размеры холста, смещение, используемые порты и
количество принимающих карт. Несовпадение размеров в имени файла с данными внутри SCR и другие
существенные изменения выводятся как предупреждения и требуют отдельного подтверждения. После
записи конфигурация повторно считывается с Taurus и проверяется. Предыдущая топология сохраняется в
локальных настройках по серийному номеру устройства, поэтому кнопка _Восстановить_ доступна и после
перезапуска GMIB. Файл SCR описывает топологию экрана; конфигурация кабинета/принимающей карты из
`*.ncp` применяется отдельно в блоке _Конфигурация кабинета_. GMIB показывает модель карты и
микросхемы из NCP и позволяет явно выбрать принимающие карты. Если NCP содержит таблицу маршрутизации
DATA, GMIB показывает экранные позиции, назначенные им физические диапазоны DATA и логические
группы. Блоки одинакового размера можно переставлять кнопками вверх и вниз: выбранный физический
DATA-диапазон переносится в указанную экранную позицию. Изменённый порядок применяется при записи или
сохраняется кнопкой _Сохранить новый NCP_ в отдельный зашифрованный файл с пересчитанной контрольной
суммой RCCB; исходный NCP не изменяется. Параметры RCCB передаются выбранным
картам напрямую с теми же паузами и проверками готовности, которые задаёт NCP. Если выбраны все карты,
GMIB использует режим NovaLCT _All Rv Cards_: записывает параметры широковещательно и проверяет
готовность каждой известной карты. Для части карт запись и проверка выполняются адресно. При применении
отображаются проверяемая карта и поблочный ход записи в байтах. После выбора файла ни одна карта не
отмечается автоматически, а недоступные карты нельзя выбрать. ADB для этого не нужен. Для встроенного
в NCP firmware GMIB раздельно показывает
версию манифеста пакета, имена образов, версии из их записей манифеста и фактические аппаратные
версии FPGA/MCU выбранных карт. Эти значения могут различаться и не используются для автоматического
решения о прошивке. Прошивка запускается только отдельной кнопкой после проверки model ID и
дополнительного подтверждения; вместе с NCP она автоматически не устанавливается. Во время операции
GMIB показывает выбранную карту, текущий файл, прогресс файла и общий процент. Для запуска и контроля
используется Taurus API, ADB не требуется. Во время прошивки нельзя отключать питание. Параметры
принимающих карт пока нельзя восстановить кнопкой
_Восстановить_: она относится только к топологии SCR.
Выбранный и разобранный NCP, целевые карты и изменённый порядок DATA сохраняются в памяти GMIB для
каждого Taurus при переходе между вкладками. Это состояние очищается при закрытии приложения.

Чтение и запись SCR/NCP, прошивка и загрузка коррекции показываются в модальном окне по центру видимой
области. Пока операция выполняется, фон, прокрутка и остальные элементы управления заблокированы.

В блоке _Коррекция с плат индикации_ выберите отдельные принимающие карты или _Все карты_ и нажмите
_Проверить платы_.
GMIB проверит память модулей и покажет количество найденных плат, их размеры и координаты в карте.
Кнопка _Загрузить с плат и сохранить_ загружает обычные коэффициенты коррекции из памяти плат в
принимающую карту и затем сохраняет их во flash карты. Память самих плат при этом не перезаписывается.
Перед загрузкой должны быть применены подходящие параметры NCP. Если подключены не все платы,
требуется отдельное подтверждение; коррекция всего кабинета в этом случае не гарантируется.
GMIB повторно проверяет платы перед загрузкой, ждёт готовности карты после каждого этапа и показывает
этап операции. Не отключайте питание до завершения. Кнопка _Восстановить_ не восстанавливает таблицу
коррекции. Поддерживаются обычные коэффициенты; отдельные таблицы низкой яркости и многослойной
коррекции этой операцией не загружаются. Для связи используются авторизация Taurus и сетевой порт
TCP/5200; USB и ADB не нужны.

Для привязки яркости экрана используйте стабильный адрес `taurus:<серийный номер>` (например,
`taurus:26721A000005306`). Можно указать только последние четыре или более символа, например
`taurus:5306`; сокращение применяется, только если ему соответствует ровно один обнаруженный Taurus.
При нескольких совпадениях GMIB не изменяет яркость и сообщает о неоднозначном серийном номере.
Адрес `taurus:*` явно выбирает все подключённые Taurus. Такая привязка продолжает работать при смене
IP-адреса, MAC-адреса и имени USB RNDIS-интерфейса. В образе gmib-kiosk RNDIS запрашивает адрес по
DHCP, а при отсутствии DHCP использует IPv4 link-local. Его шлюз и DNS не используются, поэтому TB60
не перехватывает доступ в интернет.

Параметр _Коэффициент_ автояркости может помочь, когда в режиме автояркость используются несколько
экранов с различной абсолютной яркостью. Яркость данного экрана будет рассчитана как общая яркость
(в пункте _Автояркость_) умноженная на указанный коэффициент. Если этот коэффициент равен нулю,
яркость экрана управляется индивидуально и не зависит от общей яркости.

## Автояркость

В левой части находится переключатель, который активирует режим автояркости. В этом режиме текущая
яркость рассчитывается на основе данных, поступающих от внешнего датчика освещенности. Полученные
данные об освещенности в люксах отображаются на полукруглой логарифмической шкале в верхней части
окна. При включенной автояркости GMIB автоматически ищет совместимый датчик после подключения
Siolynx, в том числе при запуске приложения с уже подключенным адаптером.

Под циферблатом находится таблица соответствия между освещенностью и яркостью. Задайте контрольные
точки зависимости яркости от данных датчика освещенности. Эти точки должны описывать монотонную
функцию, то есть при возрастании освещенности яркость не может убывать. Для показаний освещенности
удобно использовать логарифмическую шкалу, например: 100, 1000, 10000 люкс.

> Не обязательно заполнять всю таблицу, но два крайних значения являются обязательными - это
> минимальная и максимальная яркость. Также освещенность и яркость должны возрастать для каждой
> строки таблицы. Текущий уровень яркости будет вычисляться с помощью интерполяции заданных значений
> и лежать в диапазоне от минимальной до максимальной указанной яркости.

Если датчик освещенности отсутствует или неисправен, текущая яркость может быть рассчитана по высоте
солнца. Для этого вам необходимо задать текущие координаты GPS кликнув по иконке
<span class="material-symbols-outlined"> location_on </span>. В этом случае также нужно указать два
крайних значения в таблице: минимальную и максимальную яркость.

> Обратите внимание, что точные координаты должны быть записаны в десятичной нотации, а не в минутах
> и секундах!

В правом углу отображается текущая общая яркость и слайдер, с помощью которого можно ее изменять,
если не включен режим автояркости. Данная яркость будет применена ко всем экранам, для которых
включен режим автояркости (параметр _Коэффициент автояркости_ отличен от нуля).

Историю изменения яркости за последние сутки можно открыть кликнув по иконке
<span class="material-symbols-outlined"> timeline </span>. Если заданы GPS-координаты, в диалоге
также отображаются события солнца: начало рассвета, восход, заход и т.д. На графике можно включать
и отключать отдельные показания через легенду, выделять диапазон мышью и возвращаться к суточному
масштабу кнопкой _Сутки_.

## Защита от перегрева

Активируется переключателем. Защита от перегрева работает следующим образом: через определенный
_интервал_ времени считывается температура со всех модулей экрана. Далее, в зависимости от заданного
параметра _температуры_ выбирается _максимальное_, _среднее_ или _медианное_ значение и, если оно
превышает _нижнюю границу_ температурного диапазона, яркость экрана уменьшается на указанный _шаг
понижения_. Если в следующем опросе повышение температуры прекратилось, яркость не меняется. Если
температура продолжает расти или она превысила _верхнюю границу_, яркость понижается еще на один
шаг. Если температура опустилась за _нижнюю границу_, яркость начинает возвращаться к желаемому
значению также пошагово.

> Важное замечание: яркость в интерфейсе приложения - это, так называемая, желаемая яркость. Если
> включена защита от перегрева, реальная яркость может быть меньше. Ее реальное значение можно
> увидеть в свойствах устройства.

## Планировщик

Планировщик gmib запускает задания по указанной дате и времени или по повторяющемуся расписанию
cron. Можно включить или отключить тестовый вывод на выбранном экране, задать общую яркость,
включить или отключить автояркость и защиту от перегрева. Задания сохраняются между запусками и
активируются при запуске GMIB, даже если окно свернуто в трей.

При завершении GMIB планировщик прекращает запуск новых заданий. Уже выполняющееся задание
завершает работу и сохраняет результат, поэтому закрытие приложения может занять несколько секунд.

Время одиночного запуска задается с точностью до секунды. Повторяющееся расписание состоит из шести
частей cron: секунды, минуты, часы, дни месяца, месяцы и дни недели. У каждого задания есть
целочисленный приоритет; чем больше значение, тем раньше задание выполняется среди заданий с одним
временем запуска. Задания GMIB и всех плееров выполняются последовательно через общую очередь,
поэтому приоритет определяет единый порядок между ними.

Если задание _Включить тест_ запускается для теста, который уже открыт на экране, gmib заново
загружает текущую страницу теста. Это помогает восстановить тестовый вывод, если страница перестала
корректно работать после длительного показа.

## Плагины

Раздел плагинов, запуск установленных расширений и Plugin API доступны с лицензией Plus или выше.

Раздел _Плагины_ загружает официальный каталог из проекта
[`gmib-plugins`](https://github.com/sarakusha/gmib-plugins). Нажмите _Установить_ или _Обновить_ у
нужного расширения: gmib скачает соответствующий `.gmib-plugin`, сверит размер и SHA-256 с каталогом,
а затем покажет название, версию и запрошенные разрешения. После установки, обновления, включения или
отключения плагина перезапустите gmib предложенной кнопкой. Блок официального каталога по умолчанию
свёрнут; разверните его, чтобы просмотреть доступные расширения.

Для установки стороннего или локально разработанного архива нажмите _Установить из файла_.

Статические плагины содержат только HTML, CSS и JavaScript. Доверенные плагины дополнительно содержат
backend-модуль `main.cjs`, который выполняется с правами gmib. Устанавливайте доверенные плагины
только из известных источников.

Плагины хранятся отдельно от приложения в пользовательском каталоге `plugins`, поэтому обновление
gmib их не удаляет. При удалении плагина его постоянные данные сохраняются и снова станут доступны,
если установить плагин с тем же идентификатором. Страницы, объявленные плагином, автоматически
появляются в разделе _Вывод_. Если плагин предоставляет страницу управления, ее можно открыть
кнопкой _Управление_ в списке плагинов.

Для автоматизации те же операции доступны без диалогов через авторизованный lifecycle API
`/api/manage/v1/plugins`. Установка требует закрепить версию и SHA-256 и явно принять точный список
разрешений и наличие доверенного backend-кода. Архив проверяется с теми же ограничениями, что и при
локальной установке; изменения состава и состояния честно сообщают о необходимости перезапуска, но
не перезапускают gmib автоматически. Полный контракт приведен в
[`docs/ru/management-api.md`](docs/ru/management-api.md).

Для повторяемого применения экранов, плееров, плейлистов, привязок, расписаний, параметров яркости и
plugin lifecycle есть небольшой Ansible playbook в [`examples/ansible`](examples/ansible). Он
поддерживает настоящий check mode, ждет read-back после необходимого перезапуска плагинов и не
выполняет активацию, смену пароля или runtime actions без явного opt-in. Запуск и ограничения
описаны в [`docs/ru/management-ansible.md`](docs/ru/management-ansible.md).

Удаленные настройки предоставляются самим плагином через явно объявленные authenticated routes под
`/api/plugins/:pluginId`. Общего `/settings` и единой схемы для всех плагинов нет: JSON contract и
его версия принадлежат плагину и могут развиваться независимо от GMIB. Динамические plugin routes
намеренно не включены в основной OpenAPI; плагин может публиковать собственную схему.

### Формат плагина

Файл `.gmib-plugin` является ZIP-архивом с `manifest.json` в корне:

```text
parking-counter.gmib-plugin
├── manifest.json
├── dist/
│   └── main.cjs
└── public/
    ├── screen.html
    └── control.html
```

Пример манифеста:

```json
{
  "id": "parking-counter",
  "name": "Счётчик парковки",
  "version": "1.0.0",
  "gmibApi": "^1.0.0",
  "main": "dist/main.cjs",
  "public": "public",
  "permissions": ["http.routes", "storage", "realtime", "output.pages"],
  "pages": [
    {
      "id": "screen",
      "title": "Парковка/Свободные места",
      "path": "screen.html"
    }
  ],
  "control": {
    "title": "Управление",
    "path": "control.html"
  }
}
```

Plugin API версии 1 предоставляет backend-модулю следующие объекты:

- `http` — маршруты `GET`, `POST`, `PUT`, `PATCH` и `DELETE`. По умолчанию маршруты доступны только
  с локального компьютера по адресу `/plugins/<id>/api/<маршрут>`. Опция
  `{ access: "authenticated" }` размещает маршрут в авторизованном REST API
  `/api/plugins/<id>/<маршрут>`;
- `storage` — асинхронные операции `get`, `set` и атомарная `update`. Данные находятся отдельно от
  файлов плагина и сохраняются при его обновлении;
- `events.publish` — передача события клиентам WebSocket с именем
  `plugin:<id>:<имя-события>`;
- `output.registerPage` — динамическая регистрация страницы в разделе _Вывод_;
- `logger` — журнал плагина.

Разрешение из `permissions` обязательно должно быть объявлено до использования соответствующего
API. npm-зависимости backend-модуля следует заранее собрать в `main.cjs`: установка плагина не
запускает `npm install`. Исходники официальных плагинов, инструменты сборки и документация Plugin API
находятся в [`gmib-plugins`](https://github.com/sarakusha/gmib-plugins).

Базовый пример `parking-counter` показывает полный цикл Plugin API. Плагин `yoshka-esh` содержит
портретное табло 320×480 с прозрачным фоном, настраиваемой композицией и чередованием фирменной
графики. `shader-screensavers` предоставляет четыре адаптивные WebGL-заставки для подложки или
полноэкранного показа с управлением цветом, прозрачностью, скоростью и масштабом. Все три плагина
собираются и публикуются из проекта `gmib-plugins`.

## Удаленное управление

Запущенные экземпляры программы на устройствах в локальной сети (в рамках одной подсети) могут
автоматически обнаруживать друг друга. Все обнаруженные устройства перечислены в меню _GMIB_ как
имя хоста с IP-адресом. При выборе указанного пункта открывается новое окно и происходит подключение
к удаленному хосту. Если это первое подключение, то запрашивается пароль. При удачном подключении
пароль сохраняется и больше не запрашивается до его явной смены или сброса всех установок на одном
из хостов.

При открытии подключения индикатор ожидания появляется сразу, ещё до загрузки интерфейса.
Сообщения различают подключение, загрузку настроек, ошибку и закрытое соединение.
После успешного подключения краткие задержки ответов показываются предупреждением без
затемнения. Если ответы не поступают непрерывно дольше 3 секунд, управление блокируется до
восстановления связи. При закрытии соединения блокировка включается сразу; подключитесь заново.

Смена пароля удаленного управления отзывает все ранее выданные входящие подключения, включая
подключение, которым выполнена смена. После нее каждый удаленный GMIB должен снова подключиться с
новым паролем. Идентификатор устройства и сохраненные на нем подключения к другим GMIB остаются
прежними. Для автоматизации пароль преобразуется в SRP-параметры на стороне клиента и не передается
серверу открытым текстом; протокол и формат запроса описаны в
[документации REST-авторизации](docs/ru/rest-api-auth.md#смена-пароля).

> Все запросы к удаленному хосту подписываются, поэтому важно, чтобы время на обоих устройствах
> было синхронизировано. Если аутентификация не проходит, убедитесь, что время на устройствах
> совпадает.

Для разработчиков: подпись удаленного REST-запроса считается по методу, пути API вместе со строкой
запроса, timestamp и телу запроса. Query-параметры должны быть добавлены к URL до расчета подписи:
`/api/scheduler?playerId=1` и `/api/scheduler` дают разные подписи. Подробная схема описана в
[docs/ru/rest-api-auth.md](docs/ru/rest-api-auth.md).

Для автоматизации существующего REST API без Electron используйте
[`scripts/gmib-api.mjs`](scripts/gmib-api.mjs). Карта маршрутов, безопасные источники пароля и
исполняемые примеры находятся в
[`docs/ru/management-api.md`](docs/ru/management-api.md).

Параметры яркости, автояркости, локации и кривых можно читать и менять через
`/api/manage/v1/settings`; формат и runtime-ограничения описаны в
[`docs/ru/management-settings.md`](docs/ru/management-settings.md). Машиночитаемый контракт
статических маршрутов опубликован в [`docs/api/openapi.json`](docs/api/openapi.json), его границы — в
[`docs/api/README.md`](docs/api/README.md).

Новый API управления требует GMIB **5.6.0 или новее на целевом устройстве**. До публикации и
установки этой версии новые маршруты недоступны; обновление локальных скриптов не обновляет устройство.

Сохраненные удаленные хосты можно читать и атомарно синхронизировать через
`GET/PUT /api/manage/v1/hosts`. API отдельно возвращает сохраненный список и пассивно обнаруженные
mDNS endpoints, использует revision для защиты от перезаписи параллельных изменений и поддерживает
`dryRun=true`. Порт в настройке — NiBUS port; HTTP API использует следующий порт. Endpoint key
связан с нормализованными address и port и не является постоянным идентификатором устройства.

В заголовке нового окна отображается имя и адрес удаленного хоста. Теперь вы можете управлять
подключенными устройствами, как будто вы находитесь за удаленным компьютером. Если удаленное
устройство находится в другой подсети, его можно добавить в список самостоятельно через пункт меню
_Изменить список..._.

> Для удаленного взаимодействия по умолчанию используются TCP-порты 9001 и 9002. Брандмауэр и
> политика сети должны разрешать программе использовать эти соединения. Если необходимо использовать
> другие порты, задайте переменную окружения `NIBUS_PORT`: будут использоваться порты `NIBUS_PORT` и
> `NIBUS_PORT + 1`.

В Windows для автоматического обнаружения GMIB должен быть разрешен multicast DNS — входящий и
исходящий UDP-порт 5353. Если другой GMIB отвечает по HTTP, но после ожидания не найден через mDNS,
приложение покажет отдельный диалог о возможной блокировке обнаружения. В диалоге полностью видны
предлагаемые команды PowerShell: они заменяют только правила GMIB и ограничивают их текущим
исполняемым файлом. Команды следует сначала проверить, затем при необходимости скопировать и
выполнить от имени администратора, после чего полностью перезапустить GMIB. Такая проверка не
доказывает, что виноват именно Windows Firewall: UDP-порт 5353 может блокировать другой сетевой
фильтр или политика сети.

Публикация локального GMIB, поиск компьютеров для меню и выбор главного экземпляра используют один
общий mDNS-транспорт на основе `bonjour-service`. В Windows и macOS отдельный responder привязывается
к `0.0.0.0` для каждого активного IPv4-интерфейса и публикует только адрес этого интерфейса. Поэтому
системный Bonjour Service может работать одновременно с GMIB, а компьютеры обнаруживаются во всех
подключенных локальных сетях.

Каждый запущенный GMIB публикует в локальной сети собственное уникальное имя, поэтому все найденные
компьютеры одновременно отображаются в меню _GMIB_, даже если служебные имена или имена компьютеров
совпадают.

В одной подсети GMIB автоматически выбирает единственный главный экземпляр для подключения к
устройствам NovaStar. Остальные экземпляры используют его соединение через TCP-порт 9002 и не
запускают собственный сетевой поиск NovaStar. Главным становится экземпляр с наиболее новой версией
GMIB; поэтому новый GMIB автоматически заменяет старый главный экземпляр. При одинаковой версии уже
работающий главный экземпляр сохраняет роль. Случайный приоритет и уникальный идентификатор разрешают
ничью при одновременном запуске нескольких кандидатов или восстановлении после потери главного
экземпляра.

Предупреждение о рассылке NovaStar с конкретного
адреса означает, что обнаружена сторонняя программа, обычно NovaLCT. NovaLCT монопольно занимает
порт обнаружения, поэтому перед поиском устройств в GMIB ее следует закрыть.

При удаленном подключении интерфейс проверяет версию удаленного GMIB и скрывает возможности, которых
нет в этой версии. Выбор движка воспроизведения доступен с версии 4.11.0, режим масштабирования
областей вывода - с версии 4.11.1, перемотка - с версии 4.12.0, планировщики GMIB и плеера, а также
шейдеры областей вывода - с версии 5.0.0, слой `zIndex` - с версии 5.0.1, статистика
воспроизведения на SQLite - с версии 5.6.5. Отметки ошибок, повторная проверка файлов и настройки
журнала воспроизведения доступны с версии 5.6.0, путь к текущему файлу журнала — с 5.6.1.
Кнопка скрытия/показа окна вывода поддерживается удалённым GMIB начиная с 5.4.1. При подключении к более
старой версии соответствующие элементы управления не отображаются.

В Linux для точного размещения областей вывода, в том числе поверх панелей рабочего стола, включите
_Вид → Точное позиционирование окон (X11)_. Настройка отображается только для Linux и перезапускает
GMIB. Она выбирает XWayland, когда одновременно доступны Wayland и X11, поскольку нативный Wayland
не разрешает приложениям задавать абсолютные координаты обычных окон. Если WebCodecs-декодер в Linux
выдает характерную ошибку, GMIB автоматически включает программное декодирование для WebCodecs.
Этот режим можно вручную отключить в меню _Вид → WebCodecs: программное декодирование_.

## Плеер

Плеер используется для вывода медиаконтента на видеоэкраны. Окно плеера открывается через меню
_Плееры_; каждый плеер открывается в отдельном окне со своим именем. При удаленном подключении
сначала подключитесь к удаленному хосту через меню _GMIB_, затем выберите нужный плеер уже в окне
удаленного хоста.

Для верхних вкладок окна GMIB — локального GMIB, плееров и удалённых подключений — приложение
запоминает выбор в течение текущего сеанса. При закрытии активной вкладки открывается последняя
выбранная из оставшихся видимых; закрытие фоновой вкладки не меняет текущий выбор.

Основные вкладки плеера:

- _Воспроизведение_ - просмотр активного плейлиста, управление воспроизведением, выбор текущего
  плейлиста и редактирование его состава. Кнопка с глазом в тулбаре плейлиста
  скрывает или показывает области вывода текущего плеера. При удалённом подключении кнопка
  обновления в панели предпросмотра переподключает видеопоток; зависшее превью также автоматически
  переподключается, если во время воспроизведения кадры не поступают около 12 секунд. Окна вывода
  также переключаются из меню _Вид_ сочетанием `⌘⇧H` на macOS или `Ctrl+Alt+H` на Windows/Linux.
  Локальный плеер автоматически восстанавливает источник после ошибки декодирования или если позиция
  воспроизведения не меняется около 30 секунд; отдельное периодическое задание Play для этого не нужно.
  Проблемные файлы временно пропускаются и автоматически проверяются заново; если все файлы
  временно исключены, плеер остаётся запущенным и возобновляет попытки после окончания паузы.
- _Медиатека_ - загрузка медиафайлов, поиск, сортировка и удаление файлов. Загруженные файлы
  сохраняются с расширением `.mkv`; при необходимости программа конвертирует контейнер или кодек.
- _Планировщик_ - запуск действий плеера по указанной дате и времени или по повторяющемуся
  расписанию в формате cron. Можно загрузить и воспроизвести выбранный плейлист, переключить
  воспроизведение, выполнить Play, Stop, Next, скрыть или показать окно вывода, либо запустить ролик
  из текущего плейлиста по номеру. Для Stop можно дополнительно скрыть окно вывода. Для скрытия и
  показа можно выбрать все окна вывода плееров. Задания сохраняются между запусками и активируются
  при запуске GMIB. Задание можно запустить вручную для проверки действия; будущий запуск одиночного
  задания при этом сохраняется. При удаленном подключении вкладка отображается только если удаленный
  GMIB поддерживает планировщик.
  Одиночное время и cron поддерживают секунды. При одновременном запуске задания всех плееров и
  задания GMIB попадают в общую последовательную очередь: первым выполняется задание с большим
  целочисленным приоритетом.
- _Настройки_ - создание плееров, настройка областей вывода и просмотр параметров подключенных
  дисплеев.
- _Статистика_ - показатели воспроизведения за день, последние семь дней или произвольный
  период, график по дням, история попыток по ролику и экспорт CSV.

### Ошибки и журнал воспроизведения

Ошибки файлов видны в медиатеке и активном плейлисте: красная отметка сопровождается текстом
ошибки. Кнопка повторной проверки снимает запрет на воспроизведение файла. Отметки действуют
в текущем сеансе плеера; повторное открытие плеера также позволяет проверить файлы заново.

В текущем сеансе плеер запоминает по идентификатору файла, что ролик уже выдавал кадры при
воспроизведении. Одиночная ошибка такого ролика пропускает текущую попытку и позволяет повторить
его на следующем круге. Только шесть неудачных попыток без полного успешного показа включают
временный карантин на 30 секунд. Для ещё не воспроизводившихся файлов порог — три попытки,
первый карантин — 5 минут. Если пробная попытка после карантина снова неудачна, пауза удваивается
до 5 минут для ранее воспроизводившегося файла или до 30 минут для непроверенного. Истечение
паузы не прерывает текущий ролик: файл возвращается в обычную очередь. Если других файлов нет,
проверка возобновляется автоматически. Полное успешное воспроизведение сбрасывает серию ошибок
и длительность паузы; один первый кадр серию ошибок не сбрасывает. Кнопка _Повторить воспроизведение_
снимает карантин сразу. Флаг и счётчики общие для одинакового файла в разных строках плейлиста
одного плеера и сохраняются при замене источника и редактировании плейлиста, но не при закрытии плеера.

Часы декодерного воспроизведения запускаются с первого кадра, поэтому задержка открытия файла
или предзагрузка не превращает исправный короткий ролик в «опоздавший». При длительной задержке
декодирования часы подстраиваются к текущему кадру вместо отбрасывания остатка ролика; показ
может занять больше исходной длительности. Для ошибки пустого декодера журнал содержит этап
(`current`/`preload`), флаг предыдущего воспроизведения и доступные счётчики декодированных,
выданных и отброшенных кадров. Эти сведения добавляются только к ошибкам, без записи каждого кадра.

Для проверки самого декодерного конвейера есть изолированный тест
`node scripts/test-decoder-pipeline.mjs` (требуется `ffmpeg` в PATH или `FFMPEG_PATH`). Он генерирует
пятисекундный H.264/MKV, запускает настоящий Electron/WebCodecs и проверяет задержку первого
кадра, паузу, предзагрузку и возврат к первому ролику. Флаг `--compare-legacy` дополнительно
воспроизводит потерю всех кадров в прежнем регуляторе из текущей зависимости EBML. Тест не
запускает GMIB и не проверяет активацию; Linux CI запускает его через `xvfb-run`.
Успешное начало ролика не обнуляет число ошибок: повреждение в середине файла тоже приводит
к пропуску после исчерпания попыток.

### Статистика воспроизведения

Вкладка _Статистика_ расположена после _Настройки_. При удалённом подключении к GMIB версии
ниже 5.6.5, вкладка скрыта; статистика на SQLite поддерживается начиная с 5.6.5. Доступны
периоды _Сегодня_, _Вчера_, _7 дней_ (включая сегодня) и _Период_ с датами начала и окончания включительно. Даты
интерпретируются в часовом поясе хоста плеера; его название отображается рядом с выбором периода.
При удалённом подключении статистика рассчитывается на удалённом хосте.

После первого открытия вкладка сохраняет выбранный период, выход и загруженный отчёт при
переключении на другие вкладки этого плеера. Чтобы получить свежие данные, нажмите _Обновить_.
Данные сохраняются в SQLite. Отчёт строится по индексам на хосте плеера, в том числе после
перезапуска GMIB; при удалённом подключении передаются готовые итоги, а не журнал событий.

Запрошенный период автоматически ограничивается первой и последней доступной записью этого
плеера. Интерфейс показывает доступную историю и фактически учтённый интервал. Если пересечения
нет, отображается отсутствие данных. Если доступная история и учтённый интервал совпадают,
их границы показываются один раз. Дни без записей внутри периода не доказывают простой:
журнал мог быть недоступен или плеер мог не работать.

Краткая сводка объединяет показатели в группы _Время_, _Показы_ и _Ошибки и пропуски_.
Время показано в формате _Общее / Исправный вывод_ (`ЧЧ:ММ:СС` для каждого значения):
общее активное время источника учитывает все попытки, а время исправного вывода — только
завершённые попытки с наблюдаемым исправным выводом. Остальные показатели доступны в подробностях.

- _Запуски_ — попытки, в которых начался показ. Ошибка открытия файла не добавляет запуск.
- _Источник завершён_ — попытки, достигшие конца ролика. Завершение после перемотки не доказывает
  непрерывный просмотр всей исходной длительности.
- _Подтверждено_, _Частично_, _Не подтверждено_ — завершённые попытки по наблюдаемому
  состоянию выбранных выходов. Подтверждение требует наблюдения исправного вывода без известного
  сбоя. Если в одной попытке наблюдались исправный и неисправный вывод, она считается частичной.
  Скрытый выход, недоступный монитор или отсутствующее окно вывода не дают подтверждения.
  Завершение источника само по себе не подтверждает вывод.
- _Время исправного вывода_ — наблюдаемое активное время на исправном выходе только для
  завершённых попыток. Паузы, ожидание кадров, время неудачных попыток и периоды неисправного
  вывода исключаются. _Активное время источника_ учитывается отдельно, независимо от выхода.
- _Ошибки_ — сбои попыток, включая предзагрузку и повторные попытки.
- _Пропуски_ — отказ от текущего показа из-за ошибки. Не включают ручное переключение,
  остановку, смену плейлиста и фоновые обходы файлов в карантине.

Ошибка может не привести к пропуску: например, после неудачной предзагрузки файл успешно
открылся повторно. Помещение в карантин само по себе не означает количество всех потенциальных
показов за время блокировки. Прерванные вручную попытки видны в истории отдельно.
Скрытие или отключение выхода само по себе не считается ошибкой файла или пропуском.

Фильтр _Выход_ показывает показатели всех настроенных выходов или одного выхода. Таблица
_Выходы_ всегда показывает каждый настроенный выход отдельно, включая причины частичного и
неподтверждённого вывода. В истории ролика видны исход воспроизведения, состояние каждого
выхода и изменения состояния. Если сведения о выходе отсутствуют, вывод не подтверждён.
В общей сводке попытка считается один раз: подтверждение и исправное время требуют
одновременной исправности всех настроенных выходов. Время по выходам не суммируется в общее.
Состояние выхода проверяется примерно раз в пять секунд; для короткого ролика используется
последнее доступное состояние. Краткие сбои между проверками могут остаться незамеченными.

В истории ролика запуск и завершение каждой попытки показываются одной компактной строкой. Общее и
исправное время показываются только в общей статистике и CSV, без повторения в истории. Название,
дисплей и состояние выхода показываются при первом наблюдении в попытке и далее только при изменении;
неизменившиеся состояния повторно не выводятся. Неисправность отмечается мягким красным,
восстановление — мягким зелёным фоном, а текстовые метки остаются видимыми. Ошибки, пропуски, паузы
и перемотки по-прежнему отражаются в истории.

Рядом с названием выхода указано назначение дисплея, например
_Новый плеер - Вывод · Основной дисплей_. Служебные идентификаторы доступны во всплывающей подсказке.

Запуски и завершения относятся к своим моментам времени. Активное время пересекающего границу
периода ролика учитывается только внутри выбранного интервала и распределяется по календарным
дням хоста. График _Подтверждённые показы по дням_ прокручивается горизонтально: при узком окне
столбцы сохраняют минимальную ширину. Таблицу можно сортировать; нажатие на название ролика
открывает постраничную историю событий. CSV содержит выбранный фильтр, показатели по роликам,
сводку по всем выходам и границы отчёта; значения времени остаются отдельными числовыми столбцами.
Удалённые из медиатеки ролики остаются в истории
с сохранённым именем.

Статистическая история начинается с перехода на SQLite: старые дневные JSON-журналы не
импортируются и в расчёте не участвуют. При попытках с неполными данными внизу показано их
количество. Попытка без сохранённого завершения, например после аварийного закрытия GMIB,
не считается успешным показом. Учёт основан на наблюдаемом продвижении воспроизведения,
с точностью до поступления кадров/обновления позиции; он не является подтверждением
физического изображения на LED-экране.

### Хранилище и события воспроизведения

История хранится отдельно от настроек GMIB в SQLite-базе
`app.getPath('userData')/playback.sqlite`. События, попытки, активные интервалы и сведения
о выходах сохраняются при поступлении; индексы по времени, плееру и ролику позволяют строить
отчёты без повторного чтения дневных файлов. История и статистика используют одну базу.

База статистики независима от `db.sqlite3` с настройками GMIB: поток событий не использует
транзакции настройки экранов и плейлистов. Запись события атомарно обновляет связанные
таблицы; повторная доставка того же `eventId` не добавляет показ или время повторно.
SQLite работает в режиме WAL. Записи и запросы одного процесса проходят через общую очередь,
чтобы отчёт видел согласованное состояние попытки.

| Таблица | Ключ и связи | Что хранится |
| --- | --- | --- |
| `attempts` | `id` = `playbackId` | Одна попытка: `player_id`, `media_id`, номер `attempt`, `playlist_id`, `item_id`, `engine`; имя ролика; границы сохранившихся фактов `first_at`/`last_at`; отдельные моменты запуска, завершения, ошибки, пропуска и прерывания. |
| `seen_events` | `id` = `eventId`; `attempt_id` → `attempts.id` | Идентификаторы уже сохранённых событий и время `at`, включая события прогресса. Дедупликация сохраняется после перезапуска. |
| `segments` | `id` = `eventId`; `attempt_id` → `attempts.id` | Наблюдаемый активный интервал `start_at`/`end_at`, длительность `played_ms`, признак одновременной исправности всех выходов `all_showing`. |
| `segments_output` | (`segment_id`, `output_id`); `segment_id` → `segments.id` | Исправность `showing` каждого выхода внутри сегмента. Один сегмент с несколькими выходами добавляет общее время один раз. |
| `events` | `id` = `eventId`; `attempt_id` → `attempts.id` | События истории, кроме прогресса: `at`, `type`, текст `error`/`reason`, снимок выходов `output`, позиции `position`/`previous_position` и признак карантина `quarantined`. |
| `attempt_outputs` | (`attempt_id`, `output_id`); `attempt_id` → `attempts.id` | Выходы попытки: имя, назначенный и фактический дисплеи, момент наблюдения `metadata_at`; результаты и причины для первого завершающего события и отдельно для завершения ролика. |
| `output_observations` | (`player_id`, `output_id`, `at`) | Изменения имени выхода и назначения дисплея. Нужны, чтобы прошлый период показывал прежнее назначение, даже если выход позже переименовали или переназначили. |

Все поля времени `*_at` и `at` — Unix-время в миллисекундах UTC. Выбранные даты и дни отчёта
интерпретируются в часовом поясе хоста. `played_ms` имеет тип REAL: при обрезке интервала на
границе периода или хранения возможны доли миллисекунды; в отчёте время округляется. Значения
`display` и `resolved_display_id` также REAL: системный идентификатор дисплея — непрозрачное
число, а не порядковый номер монитора. Признаки `all_showing` и `showing` принимают 0 или 1;
исправность всех выходов требует непустого списка выходов. Позиции `position` и
`previous_position` — секунды внутри ролика, а не время показа; `quarantined` — необязательный
признак 0/1, не самостоятельная ошибка или пропуск.

Попытка связывает события жизненного цикла одного запуска. Сегмент — только наблюдаемая часть
активного времени этой попытки: паузы и скачки позиции при перемотке не создают длительность.
При изменении исправности выхода сегмент разделяется. События прогресса сохраняются в
числовых столбцах `segments`/`segments_output`, без JSON-копии каждого события. В `events.output`
сохраняются компактные JSON-снимки состояния для истории; списки причин результата также
хранятся как JSON. Полный журнал JSON заново не разбирается при расчёте отчёта.

В `attempts.terminal`/`terminal_at` хранится первое по времени завершение, ошибка или прерывание
для истории. `completed_at` и `completed_status` сохраняются отдельно для статистики
завершений источника; аналогично устроены результаты отдельных выходов. `started_at` означает
наблюдаемый запуск, а `declared_started_at` — переданное исходное время начала, которое может
предшествовать сохранившейся истории. Имя ролика обновляется по последнему событию с непустым
именем; если имени нет, используется `media_id`.

SQL `NULL` означает отсутствие наблюдения или необязательного контекста: например, запуск
ещё не получен, попытка не завершена, дисплей неизвестен или результат выхода не сохранён.
Это не нулевой показатель и не признак успешного показа. При отсутствии подтверждения отчёт
использует состояние «не подтверждено» и причину «состояние неизвестно»; незавершённые попытки не дают
исправное время завершённого показа. Пустой список причин `[]` отличается от неизвестных
причин. Нулевые значения в сводке означают отсутствие соответствующих фактов в периоде.

Индексы по плееру, ролику и границам попытки, времени событий и сегментов, а также
(`player_id`, `output_id`, `at`) для назначения выходов ограничивают выборку нужным периодом.
При очистке удаляются просроченные события, сегменты и идентификаторы дедупликации;
сегмент, пересекающий границу хранения, обрезается вместе с длительностью. Попытка удаляется,
когда у неё не осталось событий или сегментов. Внешние ключи с `ON DELETE CASCADE` удаляют
связанные строки выходов и сегментов. Для назначения дисплея может оставаться последнее
наблюдение перед границей хранения — как контекст ещё доступного сегмента; ненужные
наблюдения удаляются. Старые JSON-файлы очищаются отдельно, без импорта.

Событие содержит `version: 3`, уникальный `eventId` и стабильный `playbackId` попытки,
`timestamp` (ISO UTC), `playerId`, `mediaId` (MD5), `attempt`. Дополнительно сохраняются
`filename`, `playlistId`, `itemId`, `engine`, исходный `startedAt` и контекст события.
Начиная с учёта выходов, главный процесс добавляет к событиям поле `output` со снимком
`{outputs:[{id,name,display,resolvedDisplayId,state}]}`. Состояния: `showing`, `hidden`,
`unavailable` (монитор недоступен), `missing` (окно вывода отсутствует), `starting`,
`stalled`, `unknown`. Поле `outputResult` у завершающего события содержит общий
`status` (`confirmed`, `partial`, `unconfirmed`), результаты по каждому выходу и причины.
Сведения о состоянии формируются в главном процессе по его монитору выходов, а не принимаются
как утверждение renderer о состоянии нативного окна.

| Событие | Значение и дополнительные поля |
| --- | --- |
| `started` | Начало фактического воспроизведения. |
| `progress` | Наблюдаемый активный сегмент: `segmentStartedAt`, конечный `timestamp`, `playedMs`; при изменении выхода сегмент делится на части с соответствующими снимками `output`. |
| `output-changed` | Изменение наблюдаемого состояния выхода во время попытки, со снимком `output`; периодические проверки без изменения не создают запись. |
| `paused`, `resumed` | Пауза и продолжение той же попытки. |
| `seeked` | Перемотка: `previousPosition`, `position` в секундах. |
| `completed` | Достигнут конец ролика. |
| `error` | Неудачная попытка: `error`, при блокировке `quarantined: true`. |
| `skipped` | Отказ от текущего показа из-за ошибки, с `reason`. |
| `interrupted` | Прерывание при остановке, переключении ролика/плейлиста/движка, с `reason`. |
| `quarantined`, `recovered` | Диагностические изменения состояния; не добавляют показы или ошибки. |

Прогресс сохраняется с ограниченной частотой, обычно не реже чем через 15 секунд активного
продвижения, и сбрасывается перед паузой, перемоткой и результатом попытки. Сегменты не включают
скачки позиции при перемотке. Каждая часть прогресса и завершающая запись самодостаточны:
содержат данные выхода, нужные для расчёта внутри сохранённой истории. Для подсчёта
исправного времени завершённой попытки нужно связать сегменты с
`completed` по `playbackId`; повторную доставку отличать по `eventId`. Один `error` и следующая запись
`quarantined` — один сбой. Отсутствие результата не доказывает ошибку: возможен сбой процесса
или незавершённая запись события. Ошибка записи журнала не останавливает воспроизведение.

API `GET /api/playback/statistics?playerId=1&from=2026-10-01&to=2026-10-09` возвращает
сводку, строки медиа, дни, доступные/фактические границы и качество данных. Без обеих дат
используются последние семь календарных дней хоста. `GET /api/playback/statistics/history`
принимает те же параметры, обязательный `mediaId`, `offset` и `limit` (по умолчанию 50, максимум
100) для истории попыток. Максимальный `offset` — 10 000; для более ранних попыток
следует сузить период. У одной попытки отображаются до 1000 последних событий, при превышении
показывается отметка о сокращённой детализации. Доступ проходит через обычную авторизацию API хоста.

Срок хранения задаётся в _Настройки → Журнал воспроизведения_: 1–365 дней, по умолчанию 7,
включая текущий день UTC. Настройка общая для плееров хоста. Просроченные записи базы и старые
дневные `.jsonl`/`.jsonl.gz` удаляются при очистке. Очистка выполняется при запуске GMIB,
смене суток UTC и изменении срока хранения. Освобождённые страницы SQLite используются
повторно, поэтому размер файла базы может не уменьшиться сразу; блокирующий полный
`VACUUM` во время воспроизведения не выполняется. Настройки показывают полный путь к базе
статистики; при удалённом подключении это путь на удалённом хосте. Ошибка записи не прерывает
воспроизведение.


### Области вывода и шейдеры

В настройках плеера можно создать одну или несколько областей вывода. Для каждой области задаются
дисплей, координаты `X`/`Y`, ширина, высота, режим окна, режим масштабирования и, при необходимости,
GLSL-шейдер. Один плеер может одновременно выводить один и тот же активный плейлист в несколько
областей вывода.

При удаленном подключении к старым версиям GMIB настройки режима масштабирования, шейдеров и слоя
`zIndex` скрываются, если удаленный хост их не поддерживает.

При закрытии вкладки удаленного плеера остановленное окно вывода можно закрыть на удаленном хосте
по подтверждению, если удаленный GMIB версии 5.1.1 или новее; при воспроизведении или паузе окно
вывода остается открытым.

У каждой области вывода есть числовой параметр `zIndex`. Чем больше значение, тем выше будет
поднято это окно относительно окон вывода с меньшим значением. Video output окна остаются в
topmost-режиме, а порядок `zIndex` применяется внутри этой группы окон.

На Windows флаг _На весь экран_ переводит область вывода в native fullscreen/kiosk по границам
выбранного дисплея, включая область панели задач. Для обычного оконного режима заданные ширина и
высота считаются размером web-содержимого области вывода, поэтому флаг _Прозрачность_ не должен
менять фактическую геометрию окна. _Прозрачность_ нужна только когда требуется прозрачный фон или
обход артефактов compositing.

Тестовые окна вывода в разделе gmib "Вывод" поддерживают те же правила порядка: у экрана можно
задать `zIndex` и включить прозрачность фона. Чем больше `zIndex`, тем выше располагается тестовое
или видеоокно вывода относительно остальных output-окон. Встроенный тестовый виджет "Часы" выводит
текущее время по центру окна на прозрачном фоне.

Режим масштабирования определяет, как исходное видео вписывается в область вывода:

- `cover` - заполняет область целиком и обрезает края при несовпадении пропорций.
- `contain` - показывает изображение целиком и оставляет поля.
- `fill` - растягивает изображение по ширине и высоте без сохранения пропорций.
- `none` - оставляет исходный размер.
- `scale-down` - уменьшает изображение только если оно больше области вывода.

Шейдеры применяются к области вывода через WebGL. Можно выбрать готовую заготовку и изменить ее код
или написать пользовательский фрагмент. Если в коде нет `void main`, программа оборачивает его в
функцию `vec4 shader(vec2 uv, vec4 color)`, поэтому достаточно вернуть цвет пикселя, например
`return color;`.

В пользовательском фрагменте доступны:

- `uv` - координаты текущего пикселя внутри отрисованного источника в диапазоне `0.0..1.0`.
- `color` - исходный цвет пикселя `vec4`.
- `u_time` - время работы шейдера в секундах.
- `u_resolution` - размер области вывода в пикселях.
- `u_sourceResolution` - размер исходного видео в пикселях.
- `sampleSource(uv)` - чтение цвета исходного видео по указанным координатам.

Если шейдер меняет итоговые пропорции изображения, добавьте в код комментарий с подсказкой размера:
`// gmib:output-size width height`, `// gmib:output-size half-width double-height` или
`// gmib:output-aspect 1.777`. Поддерживаются токены `width`, `height`, `half-width`, `half-height`,
`double-width`, `double-height` и положительные числа. Эта подсказка влияет на расчет
масштабирования, но не меняет реальные размеры окна вывода.

Рекомендации:

- Начинайте с готовых заготовок: черно-белый, сепия, контраст, теплый/холодный тон, виньетка,
  скан-линии, CRT, хроматическая аберрация, пикселизация, волна, зеркало, калейдоскоп, контуры.
- Для нестандартных пропорций сначала выберите подходящий режим масштабирования, затем добавляйте
  `gmib:output-size` или `gmib:output-aspect`.
- Избегайте тяжелых циклов и большого числа дополнительных вызовов `sampleSource` на слабом
  оборудовании: шейдер выполняется для каждого пикселя каждого кадра.
- Если после сохранения область вывода стала пустой, проверьте GLSL-синтаксис и временно верните
  шейдер к `return color;`.

### Контроль и восстановление вывода

Во время активного воспроизведения GMIB примерно раз в 5 секунд проверяет для каждого локального
плеера существование, положение, размер и видимость native-окон вывода, а также отвечает ли
рендерер и поступают ли кадры в окна вывода. Исправляются случайно скрытые или перемещённые окна;
после пересоздания сохраняется намеренное глобальное или покадровое скрытие. Если настроенный
дисплей временно отключён, восстановление для него откладывается до возвращения дисплея.

При отсутствии кадров около 30 секунд сначала выполняется переподключение источника, ещё примерно
через 30 секунд — пересоздание окна. Если вывод не восстанавливается около 90 секунд или рендерер
не отвечает на проверки 30 секунд, перезагружается только соответствующий плеер; повторная такая
перезагрузка ограничена паузой 120 секунд. Эти интервалы являются ориентировочными: проверка
периодическая и учитывает задержки восстановления. Play может вернуть «принята» или «проверка
продолжается», пока новые кадры ещё не подтверждены. Подтверждение означает наличие кадров в
рендерере и не доказывает, что они дошли до физического LED-экрана; зависание самого GMIB или ОС
этим контролем не покрывается. События пишутся в обычный `gmib.log` с отладочными областями
`outputHealth` и `videoOut`, а не в базу статистики воспроизведения.

> Для конвертации медиафайлов нужны `ffmpeg` и `ffprobe`. На Linux их нужно установить отдельно, на
> Windows и macOS релизные сборки могут включать их в состав приложения.

# Разработка

Проект использует Node.js `>=22.12`, npm `>=10` и `pnpm`-lockfile. Основные команды:

```bash
pnpm install
pnpm run dev
pnpm run build
pnpm run test
pnpm run lint
pnpm run typecheck
```

Dev-запуск ожидает готовности всех трех preload-модулей (`gmib`, `player`, `remote`) перед
запуском Electron. При изменении main-процесса сначала завершается предыдущий Electron, затем
запускается новый; несколько изменений во время остановки объединяются в один перезапуск.
При изменении preload перезагружаются страницы. Проверка порядка запуска и остановки dev-скрипта:
`node --test scripts/watchLifecycle.test.mjs`.

Для сборки установочных пакетов используются `electron-builder` и скрипты `dist`/`release` из
`package.json`. Полная сборка с включенными `ffmpeg`/`ffprobe` ожидает подготовленные бинарные файлы
в каталоге `ffmpeg/<platform>-<arch>`; для их загрузки есть команда `pnpm run download-ffmpeg`. Для
проверки Windows-сборки без изменения релизной версии и `CHANGELOG.md` можно вручную запустить
GitHub Actions workflow `Windows Prerelease`: он публикует отдельный prerelease
`v<текущая версия>-alpha.<run>.<attempt>` с Win x64 артефактами.

## Проверочные Windows-сборки

Для проверки изменений до релиза используется отдельная ветка `prerelease` и ручной GitHub Actions
workflow `Windows Prerelease`. Он собирает только Windows x64, временно задает версию вида
`<текущая версия>-alpha.<run>.<attempt>` внутри runner, публикует GitHub prerelease и не изменяет
`package.json`, `CHANGELOG.md` или обычный draft release.

После выпуска обычного релиза синхронизируйте локальный `main` и подготовьте ветку `prerelease`:

```bash
git switch main
git pull --ff-only origin main
git switch prerelease 2>/dev/null || git switch -c prerelease
git merge --ff-only main
git push -u origin prerelease
```

Если ветка `prerelease` содержит старые экспериментальные коммиты, которые не должны сохраняться,
пересоздайте ее от текущего `main` и обновите удаленную ветку:

```bash
git switch main
git pull --ff-only origin main
git switch -C prerelease main
git push -u origin prerelease --force-with-lease
```

Дальше вносите изменения и пушьте их только в `prerelease`:

```bash
git switch prerelease
git add <files>
git commit -m "fix: describe the change"
git push
```

Запустите проверочную сборку вручную: GitHub -> Actions -> `Windows Prerelease` -> `Run workflow`,
выберите branch `prerelease` и label `alpha`. После завершения скачайте установщик из созданного
GitHub prerelease и проверьте поведение на Windows. Если нужны дополнительные исправления, повторите
цикл `commit` -> `push` -> `Windows Prerelease`; каждый запуск получит отдельный prerelease-тег.

Когда проверочная ветка готова к выпуску, перенесите ее в `main`, подготовьте релизную версию и
запушьте `main`:

```bash
git switch main
git pull --ff-only origin main
git merge --ff-only prerelease
for tag in $(git tag -l 'v*-alpha*'); do git tag -d "$tag"; done
pnpm run version:patch
git push --follow-tags origin main
```

Локальные prerelease-теги вида `v5.1.0-alpha...` нужно удалить перед запуском
`commit-and-tag-version`: иначе генератор changelog возьмет последний alpha-тег как предыдущую
версию и не включит более ранние коммиты из `prerelease` в обычный релиз. Удаление локальных
alpha-тегов не удаляет опубликованные GitHub prerelease.

Если `version:patch` уже был выполнен до удаления alpha-тегов, а release commit и тег еще не
запушены, пересоздайте release commit:

```bash
VERSION="$(node -p "require('./package.json').version")"
git tag -d "v${VERSION}"
git reset --hard HEAD~1
for tag in $(git tag -l 'v*-alpha*'); do git tag -d "$tag"; done
pnpm run version:patch
```

Для minor/major релиза используйте соответствующий режим `commit-and-tag-version`, например:

```bash
pnpm exec commit-and-tag-version -r minor
pnpm exec commit-and-tag-version -r major
```

Пуш в `main` запускает основной CI и `draft_release`, который собирает релизные артефакты для
выбранной версии.

## Перенос prerelease в main

`git merge --ff-only prerelease` работает только когда текущий `main` является прямым предком
`prerelease`. Если Git сообщает `Diverging branches can't be fast-forwarded`, значит в `main` и
`prerelease` есть разные коммиты после общего предка. Такое может случиться, например, если похожее
изменение было сделано в обеих ветках отдельными коммитами.

Для опубликованной ветки `prerelease` предпочтительно не переписывать историю, а сделать обычный
merge в `main`:

```bash
git switch main
git fetch origin
git merge --no-ff prerelease
pnpm run test
git push origin main
```

Перед merge полезно посмотреть различия:

```bash
git log --left-right --cherry-pick --oneline main...prerelease
```

> При запуске из изолированного окружения учитывайте, что GMIB проверяет конфигурационные файлы с
> подписью активации при старте. Если нужные пути конфигурации недоступны, приложение будет вести
> себя как неактивированное; такой запуск не является корректной проверкой лицензии.

### Plugin API 1.1: общие данные спортивных плагинов

Плагины могут объявлять зависимости (`dependencies`), необязательные интеграции
(`optionalDependencies`) и виды спорта (`contributes.sports`).
Зависимости загружаются первыми; ошибки одного плагина не мешают независимым плагинам.
`context.plugins.listSports()` различает установленные, включённые и готовые виды спорта.
Новые плагины указывают `gmibApi: "^1.1.0"`; существующие плагины с `^1.0.0` совместимы.

`database` открывает отдельную SQLite-базу через `context.database.open(name, migrations)`.
Данные находятся в `userData/plugins/.data/<plugin-id>/`, сохраняются при обновлении/удалении плагина.
Миграции нумеруются с 1, применяются транзакционно; изменение уже применённого SQL и откат на
несовместимую версию запрещены. Внутри `transaction` используйте переданный `tx`, а не внешний
объект базы; все операции должны быть `await`-нуты до выхода из callback.

`services.provide/consume` позволяют зависимым плагинам обмениваться типизированными сервисами,
`lifecycle.onDispose` освобождает ресурсы при завершении или ошибке активации.
`clock.now()` предоставляет монотонное время; `clock.onSuspend/onResume` — события сна компьютера.
`localOnly: true` ограничивает статические страницы и события плагина локальным компьютером.
Backend остаётся доверенным кодом, разрешения API не являются процессной песочницей.

План спортивного комплекта: [составы и хоккей](docs/ru/sports-plugins-plan.md).

### Спортивный вывод и NiBUS

Plugin API 1.1 предоставляет `output.listScreens/getStatus/start/stop` для выбора существующего
экрана gmib и сохранения профиля запуска. Плагин может включать только собственные страницы;
экран другого плагина занят. Геометрию и дисплей настройте в gmib → «Вывод» до включения из PWA.
`autoStart` восстанавливает страницу при запуске; выключение из PWA отменяет этот автозапуск.
Если дисплей отсутствует, профиль сохраняется и показывает причину, без переноса на основной монитор.
Для скрытого запуска gmib используйте существующий режим «Автозапуск».

`nibus.read/write` открывают высокоуровневый API: список соединений, `onInformationReport`,
`onConnectionChange`, `acquireOutput` и отправку таймера, счёта/периода, названий и штрафов.
Профиль `matchpad` поддерживает reports 5/50, 6/7, 8, 19/20 и 28 (два штрафа на команду).
Номера штрафов NiBUS — 0–99; PWA/LED могут работать с другими строковыми номерами.
Успешный вызов означает постановку актуального значения в очередь, не подтверждение физического
отображения. Ядро ограничивает частоту, объединяет устаревшие значения, повторяет снимок после
подключения и раз в три секунды. Одно соединение может принадлежать одному отправляющему плагину.
Сервис и serialport не выдаются backend плагина; NiBUS-сессия работает в main независимо от окна.

Локальные JSON API плагинов принимают до 20 МиБ для резервных копий и эмблем.
Спортивные плагины и их собственные инструкции находятся в репозитории gmib-plugins:
`sports-roster/README.md` и `icehockey/README.md`. `icehockey` работает и без `sports-roster`.
UDP и сетевые планшеты пока не реализованы.
