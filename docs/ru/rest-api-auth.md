# Методы авторизации интерфейса REST API

## Локальная авторизация

На стороне сервера при каждом запуске генерируется произвольная последовательность длиной 48 байт
`secret`, которая используется клиентской частью для добавления заголовка
`Authorization=Bearer ${secret.toString('base64')}` в запросы. Доступ клиентской части к `secret`
осуществляется через preload-скрипт с помощью IPC-вызова `getLocalCredentials`.

## Сетевая авторизация

Каждый экземпляр gmib получает уникальный идентификатор `identifier`, генерируемый вызовом
`nanoid()`. Также на основании пароля по умолчанию `nata-info` генерируются верификатор `verifier` и
соль `salt` по протоколу [SRP](https://ru.wikipedia.org/wiki/SRP). Полученные свойства сохраняются в
локальном конфигурационном файле. Свойство `identifier` только для чтения и при смене пароля не
изменяется. Параметры SRP для нового пароля сохраняются вместе с номером ревизии. Эта ревизия
связывает выданные сессионные ключи с паролем, при котором они были созданы.

### Аутентификация

Первоначальная аутентификация удаленного хоста осуществляется по протоколу
[SRP](https://ru.wikipedia.org/wiki/SRP) за два шага:

1. `GET /api/handshake/:id`
2. `POST /api/login/:id`

Полученный на втором шаге сессионный ключ используется для подписания запросов от хоста с
идентификатором `id` и сохраняется в локальной БД в таблице для входящих запросов `isecret` на
стороне сервера и, соответственно, в таблице для исходящих запросов `osecret` на стороне клиента,
что позволяет не требовать аутентификацию для последующих запросов. Для повторной аутентификации
достаточно удалить запись в БД на стороне сервера и/или клиента.

Незавершенный handshake действует 10 секунд и используется один раз. После проверки формата полей
`A` и `M1` сервер извлекает handshake из очереди до проверки SRP-доказательства, поэтому повторить
login с тем же handshake нельзя даже после неверного доказательства. Запрос с некорректным JSON или
форматом полей отклоняется до извлечения handshake. Число одновременно незавершенных handshake
ограничено. Идентификатор клиента должен состоять из латинских букв, цифр, `_` и `-` и содержать не
более 128 символов. Передача `salt` или `verifier` в `/api/login/:id` больше не меняет пароль и
возвращает ошибку `password_rotation_moved`.

### Смена пароля

Пароль меняется запросом `PUT /api/manage/v1/auth/password`. Клиент самостоятельно вычисляет по
новому паролю SRP-параметры и отправляет только JSON-объект
`{ "salt": "0x...", "verifier": "0x..." }`. Сам пароль серверу не передается. Запрос требует обычной
Bearer- или сетевой SRP/HMAC-авторизации даже при включенном `unsafeMode` и доступен до активации
лицензии.

После успешного ответа сервер отзывает все входящие сетевые сессии и незавершенные handshake,
включая сессию, которой был подписан запрос. Ответ содержит `{ "reauthenticateRequired": true }`:
всем удаленным клиентам нужно снова выполнить handshake/login с новым паролем. Идентификатор этого
GMIB и сохраненные исходящие подключения к другим GMIB не изменяются. Если две сетевые сессии
одновременно пытаются сменить пароль, применяется только запрос, авторизованный актуальной ревизией;
остальные получают `authorization_stale`.

Если сохранить новую пару `salt`/`verifier` не удалось, сервер возвращает `rotation_failed`, пароль
остается прежним и действующие сессии не отзываются. Ошибка `revocation_incomplete` означает, что
новый пароль уже сохранен, но физическая очистка старых записей сессий завершилась ошибкой. Эти
записи блокируются новой ревизией; клиенту нужно выполнить handshake/login с новым паролем и при
необходимости проверить текущее состояние новым авторизованным запросом. Повторять старый
подписанный запрос смены пароля бессмысленно: его авторизация уже отозвана.

SRP не передает пароль по сети, а HMAC подтверждает целостность и автора запроса, но эти механизмы
не шифруют HTTP-трафик. Для управления через недоверенную сеть используйте защищенный канал,
например VPN или TLS-прокси.

### Авторизация

Каждый запрос от клиента должен содержать заголовки:

- `x-ni-identifier` - `identifier` клиента;
- `x-ni-timestamp` - время создания запроса;
- `x-ni-signature` - подпись, сгенерированная на основе сессионного ключа.

Подпись вычисляется функцией `generateSignature(apiSecret, method, uri, timestamp, body)`.
Подписываемый `uri` должен содержать путь API вместе со строкой запроса, но без схемы, хоста и
порта. Фактически `generateSignature` нормализует переданный URI до `pathname + search` и считает
HMAC-SHA256 по строке:

```text
METHOD + PATH_AND_QUERY + TIMESTAMP + BODY
```

Например, запрос `GET /api/scheduler?playerId=1` должен подписываться именно как
`/api/scheduler?playerId=1`. Если клиентская обертка принимает query-параметры отдельно, их нужно
добавить к URL до расчета подписи. Подпись для `/api/scheduler` не подойдет для фактического запроса
`/api/scheduler?playerId=1`.

Тело запроса добавляется в HMAC только если оно есть и не является пустым объектом. При сетевых
запросах клиент получает сессионный ключ через preload-скрипт с помощью IPC-вызова
`getRemoteCredentials`.

### Свободные ресурсы

Следующие ресурсы доступны неавторизованным клиентам:

- `/api/handshake/*` - 1 шаг аутентификации;
- `/api/login/*` - 2 шаг аутентификации;
- `/api/identifier` - запрос идентификатора;
- `/api/novastar/subscribe` - подписка на события novastar.
